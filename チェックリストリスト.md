結論として、現状は**Vulkan の初期化・単純な描画・将来拡張用の骨格**としては良いですが、AAA 対応に必要な「大量アセット」「複数レンダリングパス」「非同期処理」「GPU メモリ寿命管理」「デバッグ・計測」を支える基盤はまだ未実装です。

特に優先すべきなのは、**Frame Graph の実装完成、GPU リソース管理、描画データの GPU-driven 化、マルチスレッド／非同期実行、シェーダー・マテリアル体系の再設計**です。

## 現状の構成

README の構想どおり、C++23、Vulkan、VMA、GLFW、GLM、FlatBuffers、fastgltf、Slang を使い、`engine/renderer` 以下を Vulkan backend・scene・techniques・frame graph に分けています。

主な既存要素は以下です。

- `VulkanRenderer`
    - Vulkan 初期化
    - Swapchain
    - UBO
    - Bindless texture
    - メッシュ登録
    - フレーム描画
- `scene/`
    - カメラ
    - glTF ローダー
    - メッシュ
    - Transform
- `vulkan/frame_graph/`
    - Pass
    - Image/Buffer resource handle
    - Graph compiler
    - Graph executor
- `techniques/pbr` / `techniques/toon`
    - レンダリング技法の分離予定
- `assets/shaders/main.slang`
    - Global UBO
    - Bindless texture
    - Push Constants
- `schemas/`
    - FlatBuffers による RenderCommand、Scene、FrameSnapshot

ただし Frame Graph は現在、型とインターフェースが中心で、`ExecutionPlan` にバリアがまだ存在せず、`ExecutionContext` も実質的に `VkCommandBuffer` だけです。`draw_frame()` は Frame Graph を経由せず、直接レンダリングパスを記録しています。

# AAA 対応アーキテクチャ・チェックリスト

## 1. レンダラー全体の責務分離

### 必須

- [ ] `VulkanRenderer` から Vulkan 初期化処理を分離する
- [ ] `VulkanContext` を Instance／Device／Queue／Allocator の所有者に限定する
- [ ] `RenderDevice` または `GraphicsDevice` API を導入する
- [ ] `Renderer` と `VulkanBackend` を分離する
- [ ] Scene、Visibility、Material、Resource、Pass の責務を分離する
- [ ] `draw_frame()` にすべての描画ロジックを集約しない
- [ ] Renderer の public API から Vulkan 型を可能な限り隠す
- [ ] C ABI の `execute_render_command()` と C++ Renderer API の役割を統一する

### 推奨する層

```text
Renderer API
  ├── RenderWorld / SceneSnapshot
  ├── VisibilitySystem
  ├── RenderPipeline
  ├── FrameGraph
  ├── ResourceSystem
  ├── ShaderSystem
  ├── MaterialSystem
  └── VulkanBackend
        ├── Device
        ├── Queue
        ├── Swapchain
        ├── CommandContext
        ├── DescriptorSystem
        └── GPU Memory
```

現在の `VulkanRenderer` は、Swapchain、同期、メッシュ、テクスチャ、Descriptor、Pipeline、Scene loading まで保持しており、AAA 規模では責務過多になります。`engine/renderer/vulkan/render/vulkan_renderer.h` の `VulkanRenderer` は、段階的に facade 化するべきです。

## 2. Frame Graph

これは最優先です。

### 必須

- [ ] Resource の仮想 ID と実際の `VkImage`／`VkBuffer` の対応表を実装する
- [ ] Pass の依存関係を自動構築する
- [ ] トポロジカルソートを実装する
- [ ] Read-after-write、Write-after-read、Write-after-write を検出する
- [ ] `VkDependencyInfo` と `VkImageMemoryBarrier2` を自動生成する
- [ ] `VK_KHR_synchronization2` を標準化する
- [ ] Image layout transition を Frame Graph が管理する
- [ ] transient resource の aliasing を実装する
- [ ] Resource lifetime を pass の範囲から計算する
- [ ] 未使用 pass／未使用 resource を削除する
- [ ] Pass の debug name と GPU marker を設定する
- [ ] Graph のコンパイル結果を可視化できるようにする
- [ ] Swapchain resize 時に graph を再構築する

現在の `render_graph_types.h` では `ExecutionPlan` に `sorted_passes` はありますが、バリアはコメント状態です。また `graph_executor.h` の `ExecutionContext` には実質的に command buffer しかありません。AAA 向けには、少なくとも以下の情報が必要です。

  ├── resource registry
  ├── descriptor allocator
  ├── upload context
  ├── pipeline cache
  ├── GPU timestamp context
  └── pass-local transient allocations

- [ ] Alpha-tested

- [ ] SSAO／SSGI
- [ ] SSR または Reflection
- [ ] Volumetric／Fog
- [ ] Bloom
- [ ] Tone mapping
- [ ] UI／Debug
- [ ] Present

## 3. フレーム管理と GPU 同期

現在は `MAX_FRAMES_IN_FLIGHT` と fence／semaphore を使った基本形ですが、AAA 規模ではさらに必要です。

### 必須

- [ ] Frame context を導入する
- [ ] フレームごとの command pool を持つ
- [ ] フレームごとの descriptor pool／descriptor arena を持つ
- [ ] フレームごとの upload ring buffer を持つ
- [ ] フレームごとの transient allocator を持つ
- [ ] CPU frame number と GPU completion point を管理する
- [ ] timeline semaphore を導入する
- [ ] binary semaphore から timeline semaphore 中心へ移行する
- [ ] Graphics／Compute／Transfer queue を分離する
- [ ] queue family ownership transfer を扱う
- [ ] CPU-GPU 同期を `vkDeviceWaitIdle()` 依存にしない
- [ ] resource destruction を deferred destruction にする
- [ ] fence 完了後ではなく timeline value 到達後にリソースを破棄する
- [ ] swapchain の `OUT_OF_DATE`／`SUBOPTIMAL` 処理を完成させる
- [ ] resize、minimized window、HDR swapchain を処理する

現在、`VulkanRenderer` の destructor や move assignment は `vkDeviceWaitIdle()` に依存しています。これは安全ではありますが、ストリーミングや非同期リソース更新のあるエンジンではボトルネックになります。

## 5. 描画データの GPU-driven 化

現在の描画は `snapshot.instances` を CPU でループし、インスタンスごとに Push Constants、vertex buffer bind、index buffer bind、draw を行っています。`vulkan_renderer_draw.cpp` のこの構造は、少数オブジェクトのデモとしては十分ですが、大量描画には向きません。

### 必須

- [ ] Instance data を GPU buffer にアップロードする
- [ ] `SV_InstanceID` または `gl_InstanceIndex` でデータを取得する
- [ ] Push Constants の model matrix 依存を廃止する
- [ ] indirect draw buffer を導入する
- [ ] `vkCmdDrawIndexedIndirectCount` を導入する
- [ ] GPU frustum culling を実装する
- [ ] GPU occlusion culling を実装する
- [ ] LOD selection を GPU または並列 CPU で行う
- [ ] meshlet／cluster 単位の描画に対応する
- [ ] visibility buffer または compacted visibility list を検討する
- [ ] material／mesh ごとに draw をソートする
- [ ] pipeline state の切り替えを最小化する
- [ ] bindless resource index を安定した ID として管理する

### 推奨する描画データ

```text
InstanceBuffer
  ├── transform
  ├── previous_transform
  ├── mesh_id
  ├── material_id
  ├── skinning_offset
  ├── flags
  └── bounding_sphere

DrawItemBuffer
  ├── index_count
  ├── first_index
  ├── vertex_offset
  ├── instance_offset
  └── material_id

IndirectDrawBuffer
  └── VkDrawIndexedIndirectCommand[]
```

`render_graph_types.h` には `InstanceData` と `SkinnedInstanceData` の構想が既にあるため、これを実際の GPU-driven pipeline に接続するのが自然です。
