はい。現在の Vanta の実装状況を反映すると、以前のチェックリストは「未実装項目の一覧」から、**依存関係を持つ実装ロードマップ**へ整理した方がよいです。

現時点では、Frame Graph の以下はすでに存在します。

- generation 付き `ImageHandle`／`BufferHandle`
- image／buffer resource の作成・import
- Pass の read/write 宣言
- dependency graph 構築
- トポロジカルソート
- usage から Vulkan synchronization state への変換
- cycle detection
- barrier 計画の生成準備

一方で、[`graph_executor.cpp`](https://github.com/nebula-ray48/Vanta/blob/923559a64925ba7377e98f22891a3d000e9b279e/engine/renderer/vulkan/frame_graph/graph_executor.cpp) はまだ barrier を Vulkan に記録しておらず、[`vulkan_renderer_draw.cpp`](https://github.com/nebula-ray48/Vanta/blob/923559a64925ba7377e98f22891a3d000e9b279e/engine/renderer/vulkan/render/vulkan_renderer_draw.cpp) は直接 `vkCmdPipelineBarrier`、`vkCmdBeginRendering`、draw、present を記録しています。

そのため、最初の目標は「AAA 機能を増やすこと」ではなく、

> **現在の MainColor 描画を壊さずに、Vulkan 基盤と Frame Graph の責務を確立すること**

です。

# P1: Vulkan backend の責務分離

現状の [`vulkan_context.h`](https://github.com/nebula-ray48/Vanta/blob/923559a64925ba7377e98f22891a3d000e9b279e/engine/renderer/vulkan/core/vulkan_context.h) は Instance、Device、Queue、VMA allocator、`GpuBuffer` まで保持しています。また [`sync_context.h`](https://github.com/nebula-ray48/Vanta/blob/923559a64925ba7377e98f22891a3d000e9b279e/engine/renderer/vulkan/core/sync_context.h) は command pool、command buffer、semaphore、fence をまとめています。

この状態は初期実装としては許容できますが、次の段階で分ける必要があります。

## 推奨構成

```text
engine/renderer/vulkan/
  device/
    vulkan_instance
    vulkan_device
    queue_context

  swapchain/
    swapchain_manager

  frame/
    frame_context
    frame_scheduler

  commands/
    command_context
    command_pool

  memory/
    gpu_allocator
    upload_context
    deferred_destroy

  resources/
    gpu_buffer
    gpu_image
    resource_registry

  descriptors/
    descriptor_allocator
    bindless_table

  pipeline/
    pipeline_cache
```

## 実装項目

- [ ] `VulkanContext` から `VulkanDevice` を分離
- [ ] Graphics queue と queue family 情報を `QueueContext` へ分離
- [ ] `SwapchainTarget` を `SwapchainManager` へ改名または責務整理
- [ ] `SyncContext` を `FrameContext` の配列へ移行
- [ ] frame-local command pool を導入
- [ ] frame-local descriptor pool の設計を追加
- [ ] `VulkanRenderer::create()` を subsystem 初期化の orchestration に限定
- [ ] `VulkanRenderer` から scene loading を分離
- [ ] `VulkanRenderer` から texture loading を分離
- [ ] resource destruction の順序を subsystem ごとに明文化
- [ ] `vkDeviceWaitIdle()` を通常の resource 更新で使わない方針にする

## 完了条件

- `VulkanRenderer` が Device／Swapchain／FrameScheduler／GraphExecutor を組み合わせる facade になる
- Vulkan 初期化、frame synchronization、scene loading が別 subsystem に分かれる
- 各 subsystem に単独のテストまたは validation path がある
- `VulkanRenderer` の destructor が全 resource を直接列挙しない

しかし [`graph_executor.cpp`](https://github.com/nebula-ray48/Vanta/blob/923559a64925ba7377e98f22891a3d000e9b279e/engine/renderer/vulkan/frame_graph/graph_executor.cpp) は barrier を TODO のまま、Pass callback だけを実行しています。

## 実装項目

- [ ] `ExecutionPlan` に pass 名または元 pass index を保持
- [ ] `ExecutionContext` に ResourceRegistry を追加
- [ ] `ExecutionContext` に frame index を追加
- [ ] `PassContext` を導入
- [ ] ImageHandle から `VkImage`／`VkImageView` を解決
- [ ] BufferHandle から `VkBuffer` を解決
- [ ] `VkImageMemoryBarrier2` を生成
- [ ] `VkBufferMemoryBarrier2` を生成
- [ ] `VkDependencyInfo` を生成
- [ ] `vkCmdPipelineBarrier2` を実行
- [ ] pass 前 barrier を実行
- [ ] pass callback を実行
- [ ] debug label を pass ごとに開始／終了
- [ ] null callback をエラーまたは明示的な no-op として扱う
- [ ] image／buffer の barrier を分離
- [ ] imported resource の initial state を正しく扱う
- [ ] `Present` 用の final state を処理する

## Usage 定義の整理

現在の `UsageType` は `ColorAttachment`、`DepthAttachment`、`ShaderRead`、`ComputeWrite` などを持ち、compiler の同期変換もすでにあります。

次に必要なのは、Usage と Vulkan state の対応をテストで固定することです。

- [ ] `Undefined -> ColorAttachment`
- [ ] `ColorAttachment -> ShaderRead`
- [ ] `ShaderWrite -> ShaderRead`
- [ ] `TransferDst -> ShaderRead`
- [ ] `ColorAttachment -> Present`
- [ ] Buffer の `TransferDst -> VertexRead`

## 完了条件

- Graph executor が `vkCmdPipelineBarrier2` を実行する
- Pass callback が `PassContext` 経由で resource にアクセスする
- compiler が生成した barrier と executor の実行内容が一致する
- `ColorAttachment -> Present` の transition が自動生成される
- Frame Graph 単体テストで barrier が検証できる
