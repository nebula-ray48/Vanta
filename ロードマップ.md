はい。その順番が最も安全です。  
いきなり PBR、TAA、GPU culling へ進むより、まず **Vulkan 基盤の責務整理 → Frame Graph の最小実装 → 現在の描画を Graph 経由に移行**するべきです。

## 推奨ロードマップ

```text
Phase 0  現状を固定
Phase 1  Vulkan基盤の責務分離
Phase 2  Frame Context / Resource管理
Phase 3  Frame Graphの最小実装
Phase 4  現在の描画をFrame Graphへ移行
Phase 5  Depth / Upload / Debug基盤
Phase 6  複数Render Passへ拡張
```

# Phase 1: Vulkan 基盤を整理する

現状の `VulkanRenderer` は以下を同時に所有しています。

- Vulkan Context
- Swapchain
- Sync
- Mesh
- Texture
- Descriptor
- Pipeline
- Frame recording
- Scene loading

まず、これを以下の単位へ分けます。

```text
engine/renderer/vulkan/
  device/
    vulkan_instance
    vulkan_device
    queue_context

  memory/
    gpu_allocator
    upload_context
    deferred_destroy_queue

  resources/
    buffer
    image
    image_view
    sampler
    resource_registry

  descriptors/
    descriptor_allocator
    bindless_table

  commands/
    command_context
    command_pool

  swapchain/
    swapchain
    swapchain_target

  frame/
    frame_context

  pipeline/
    pipeline
    pipeline_cache
```

## 最初に分離するクラス

### `VulkanDevice`

担当:

- `VkInstance`
- `VkPhysicalDevice`
- `VkDevice`
- Queue family
- Graphics／Compute／Transfer queue
- Feature／extension capability

```cpp
class VulkanDevice {
public:
    VkDevice device() const noexcept;
    VkQueue graphics_queue() const noexcept;
    VkQueue compute_queue() const noexcept;
    VkQueue transfer_queue() const noexcept;

    bool supports_descriptor_indexing() const noexcept;
    bool supports_synchronization2() const noexcept;
};
```

`VulkanContext` にすべてを詰め込むのではなく、まず Device と Queue の責務を明確にします。

### `SwapchainManager`

担当:

- Swapchain 作成・破棄
- Image／ImageView
- Resize
- `VK_ERROR_OUT_OF_DATE_KHR`
- `VK_SUBOPTIMAL_KHR`
- Present mode
- HDR format

`VulkanRenderer::begin_frame()` にある acquire 処理と、present 処理は、最終的に Swapchain manager へ寄せます。

### `FrameContext`

フレームごとに持つものです。

```cpp
struct FrameContext {
    uint32_t frame_index;

    VkCommandPool graphics_command_pool;
    VkCommandBuffer graphics_command_buffer;

    VkCommandPool compute_command_pool;
    VkCommandBuffer compute_command_buffer;

    VkFence completion_fence;
    VkSemaphore image_available;
    VkSemaphore render_finished;

    DescriptorArena descriptor_arena;
    UploadArena upload_arena;
    DeferredDestroyQueue deferred_destroy;
};
```

最初は binary semaphore と fence のままでも構いません。  
Timeline semaphore は Frame Graph の基本動作が安定した後に追加した方が切り分けしやすいです。

# Phase 2: Resource 管理を先に作る

Frame Graph は Vulkan resource を直接生成・破棄する仕組みにしない方がよいです。

まず、Graph から参照できる resource registry を作ります。

```text
ResourceRegistry
  ├── BufferHandle -> GpuBuffer
  ├── ImageHandle -> GpuImage
  ├── ImageViewHandle -> VkImageView
  ├── SamplerHandle -> VkSampler
  └── ResourceState
```

## Handle は Vulkan handle と分離する

現在の Frame Graph には以下があります。

```cpp
struct ImageHandle { uint32_t id; };
struct BufferHandle { uint32_t id; };
```

これは良い方向です。ただし、世代番号を追加してください。

```cpp
struct ImageHandle {
    uint32_t index;
    uint32_t generation;
};

struct BufferHandle {
    uint32_t index;
    uint32_t generation;
};
```

これにより、解放済み resource の古い ID を誤って使う問題を検出できます。

## Resource description を拡張する

現在の `ImageDescription` は width、height、format が中心です。最低限、以下を追加します。

```cpp
struct ImageDescription {
    uint32_t width;
    uint32_t height;
    uint32_t mip_levels;
    uint32_t array_layers;

    VkFormat format;
    VkImageType type;
    VkImageUsageFlags usage;
    VkImageCreateFlags flags;
    VkSampleCountFlagBits samples;

    bool transient;
    bool imported;
    bool external;
};
```

Buffer も必要です。

```cpp
struct BufferDescription {
    VkDeviceSize size;
    VkBufferUsageFlags usage;

    bool transient;
    bool imported;
    bool external;
};
```

## Ownership を明確にする

各 resource について、以下のどれかを明確にしてください。

```text
Imported
  Swapchain image など、外部が所有する resource

Transient
  Frame Graph が作成し、フレーム内だけ使用する resource

Persistent
  フレームをまたいで保持する resource

External
  Asset system や renderer 外部が所有する resource
```

この区別がないと、Frame Graph が resource を破棄してよいか判断できません。

# Phase 3: Frame Graph の最小実装

最初から aliasing、async compute、複数 queue まで実装する必要はありません。

最初の目標は、現在の描画を以下の Graph として実行することです。

```text
Acquire Swapchain
        ↓
Main Color Pass
        ↓
Present
```

## Pass API

現在の `PassBuilder` は方向性として問題ありません。

```cpp
auto graph = RenderGraphBuilder{};

auto backbuffer = graph.import_image(
    swapchain_image,
    swapchain_description);

graph.add_pass("MainColor",
    [&](PassBuilder& pass) {
        pass.write_image(
            backbuffer,
            UsageType::WRITE_COLOR);

        pass.set_execute(
            [](PassContext& context) {
                // vkCmdBeginRendering
                // draw
                // vkCmdEndRendering
            });
    });

auto compiled = graph.compile();
```

`execute(VkCommandBuffer)` だけでは情報不足になるので、`PassContext` を導入するのが重要です。

```cpp
class PassContext {
public:
    VkCommandBuffer command_buffer() const noexcept;

    VkImage image(ImageHandle handle) const noexcept;
    VkImageView image_view(ImageHandle handle) const noexcept;
    VkBuffer buffer(BufferHandle handle) const noexcept;

    const ResourceRegistry& resources() const noexcept;
};
```

Pass callback が `VkImage` や `VkImageView` を直接保持しないようにします。

# Phase 4: Graph Compiler の実装順

`compile_graph()` は、以下の順番で実装するとよいです。

## 4.1 Resource 宣言の収集

各 pass が何を読むか、何に書くかを収集します。

```text
Pass A:
  write Color

Pass B:
  read Color
  write Present
```

## 4.2 依存関係の構築

最初は同一 resource に対する書き込みと読み込みだけで十分です。

```text
Pass A -> Pass B
```

## 4.3 トポロジカルソート

`sorted_passes` を生成します。

```cpp
struct ExecutionPlan {
    std::vector<CompiledPass> passes;
    std::vector<ResourceBarrier> barriers;
};
```

現在の `ExecutionPlan` にある `std::vector<VkImageMemoryBarrier2>` のコメント部分は、まず抽象 barrier にした方が扱いやすいです。

```cpp
struct ResourceBarrier {
    ResourceId resource;

    ResourceState before;
    ResourceState after;

    VkPipelineStageFlags2 src_stage;
    VkPipelineStageFlags2 dst_stage;
    VkAccessFlags2 src_access;
    VkAccessFlags2 dst_access;
};
```

その後、backend で `VkImageMemoryBarrier2` と `VkBufferMemoryBarrier2` に変換します。

## 4.4 Barrier の生成

初期実装では、各 resource の直前 state を追跡します。

```text
Undefined
  -> ColorAttachment
  -> ShaderRead
  -> Present
```

最初に対応する Usage は以下で十分です。

```cpp
enum class UsageType {
    Undefined,
    ColorAttachment,
    DepthAttachment,
    ShaderRead,
    ShaderWrite,
    TransferSrc,
    TransferDst,
    Present,
};
```

現在の `READ_TEXTURE`、`WRITE_COLOR` などは、最終的に Vulkan の stage、access、layout に変換できる定義へ整理してください。

# Phase 5: 現在の `draw_frame()` を Graph に移行する

この段階で重要なのは、既存の描画結果を変えずに、記録経路だけを Graph 化することです。

現在の `vulkan_renderer_draw.cpp` はおおむね以下を直接実行しています。

```text
wait fence
acquire image
reset command buffer
begin command buffer
barrier: undefined -> color attachment
begin rendering
bind pipeline
bind descriptors
draw meshes
end rendering
barrier: color attachment -> present
submit
present
```

これを次のように分割します。

```text
begin_frame
  ├── wait frame completion
  ├── acquire swapchain image
  └── create frame context

build_frame_graph
  ├── import swapchain image
  └── add MainColorPass

compile_frame_graph
  ├── dependency analysis
  ├── resource state analysis
  └── barrier generation

execute_frame_graph
  ├── begin command buffer
  ├── emit pre-barriers
  ├── execute MainColorPass
  ├── emit post-barriers
  └── end command buffer

submit_and_present
```

最初の `MainColorPass` は、既存の以下の処理をそのまま移してください。

- `vkCmdBeginRendering`
- Pipeline bind
- Descriptor bind
- Mesh draw
- `vkCmdEndRendering`

つまり、最初から描画ロジックまでリファクタリングしないことが重要です。

---

# 最初に作るべき Pass

## 1. `MainColorPass`

```text
Input:
  - SceneSnapshot
  - CameraData
  - MeshRegistry
  - MaterialRegistry

Output:
  - Swapchain color image
```

## 2. `PresentPass`

実際には Present 自体は queue operation ですが、Graph 上で Present usage を宣言します。

```text
MainColorPass
  writes: SwapchainImage as ColorAttachment

Present
  reads: SwapchainImage as Present
```

## 3. `ClearPass`

テスト目的で clear 処理だけを独立 Pass にしておくと、barrier と resource state の確認が簡単になります。

```text
ClearPass
  writes: TestColor as ColorAttachment
```

# Depth は Frame Graph の後に追加

Frame Graph へ移行した直後に Depth を追加するのがよいです。

```text
DepthPrepass
  writes: DepthImage as DepthAttachment

OpaquePass
  reads: DepthImage as DepthRead
  writes: ColorImage as ColorAttachment

PresentPass
  reads: ColorImage as Present
```

Depth image は Swapchain image と違い、Graph 内で作成する persistent resource にします。

```text
DepthImage
  ├── created on swapchain creation
  ├── recreated on resize
  └── destroyed after GPU completion
```

この時点で、Graph が以下を正しく扱えるようになります。

- Color attachment
- Depth attachment
- Depth read
- Present transition
- Resize に伴う resource 再生成

# 完了条件

Frame Graph 導入の第一段階は、次の状態になれば成功です。

```text
VulkanRenderer
  ├── begin_frame()
  ├── build_render_graph()
  ├── compile_render_graph()
  ├── execute_render_graph()
  └── present()
```

そして、以下が成立していることです。

- 描画結果が Frame Graph 導入前と同じ
- `vulkan_renderer_draw.cpp` に手書きの image barrier がない
- Pass が Vulkan の raw resource を所有していない
- Swapchain image が imported resource として扱われる
- Graph compiler が pass 順序を決める
- Graph executor が barrier を挿入する
- Resize 時に Graph と Depth resource を再構築できる
- Validation Layer のエラーがない
- RenderDoc 上で Pass 名が確認できる

この段階まで進めれば、以後は同じ仕組みで `ShadowPass`、`GBufferPass`、`LightingPass`、`PostProcessPass` を追加できます。つまり、今は機能を増やすよりも、**「描画処理を Pass と Resource の宣言へ変換できる基盤」を完成させること**が最優先です。
